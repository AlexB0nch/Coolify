# Coolify на 95.85.242.143

Разворачивание чистой Ubuntu-VPS в PaaS: SSH-ключи, базовая защита, Coolify.
Дальше новые сайты добавляются в UI за пару минут, TLS и поддомены — автоматом.

## Быстрый старт

Три команды у себя в терминале (macOS / Linux / WSL / Git Bash).
Пароль root спросят **один раз**, в первой команде.

> **Windows:** запускать надо именно в bash, а не в PowerShell — в PowerShell 5.1
> нет ни `&&`, ни перенаправления `< файл`. Набери `bash`, нажми Enter и все
> команды ниже выполняй уже внутри него. Если `ssh` в WSL не найден:
> `sudo apt update && sudo apt install -y openssh-client`.

```bash
git clone https://github.com/AlexB0nch/Coolify.git coolify-setup && cd coolify-setup

# 1. ключи: создать, залить на сервер, прописать алиас `coolify`
bash scripts/01-local-keys.sh

# 2. сервер: обновление, пользователь, swap, firewall, fail2ban, Coolify
ssh coolify 'bash -s' < scripts/02-server-setup.sh
```

Открываешь `http://95.85.242.143:8000`, **сразу** заводишь админа — регистрация
открыта до первого пользователя. Затем, убедившись, что `ssh coolify` пускает
без пароля:

```bash
# 3. закрыть вход по паролю
ssh coolify 'bash -s' < scripts/03-harden-ssh.sh
ssh coolify 'echo вход по ключу работает'   # проверка в новом окне
```

Диагностика в любой момент: `ssh coolify 'bash -s' < scripts/04-status.sh`

## Что делает каждый скрипт

| Скрипт | Где | Что |
|---|---|---|
| `01-local-keys.sh` | твой компьютер | ed25519-ключ `~/.ssh/coolify_ed25519`, заливка на сервер, алиас `coolify` в `~/.ssh/config`, проверка входа |
| `02-server-setup.sh` | сервер, root | apt upgrade, sudo-пользователь `deploy`, swap 2 ГБ при RAM < 4 ГБ, ufw (22/80/443/8000), fail2ban, unattended-upgrades, установка Coolify |
| `03-harden-ssh.sh` | сервер, root | `PasswordAuthentication no`, root — только по ключу |
| `04-status.sh` | сервер | состояние: память, диск, firewall, контейнеры, порты |
| `05-deploy-worker.sh` | твой компьютер | разворачивает воркер из приватного репозитория через API Coolify: ключ, проект, приложение, переменные окружения |

Переменные, если нужно отойти от умолчаний:

```bash
SERVER_IP=1.2.3.4 HOST_ALIAS=myserver bash scripts/01-local-keys.sh
ssh coolify 'NEW_USER=admin SWAP_SIZE=4G bash -s' < scripts/02-server-setup.sh
```

## DNS

Одна wildcard-запись закрывает все будущие проекты — новый сайт не требует
никаких действий в DNS:

```
A    coolify.твойдомен.ru   ->  95.85.242.143
A    *.твойдомен.ru         ->  95.85.242.143
A    твойдомен.ru           ->  95.85.242.143
```

После того как DNS разъехался (`dig coolify.твойдомен.ru +short`):
Coolify → **Settings → Instance Domain** → `https://coolify.твойдомен.ru`.
Панель переедет на HTTPS, и порт 8000 можно закрыть:

```bash
ssh coolify 'ufw delete allow 8000/tcp'
```

## Первый проект

1. **Sources** → подключить GitHub (Coolify создаст GitHub App, доступ по репозиториям).
2. **Projects → New → Application** → репозиторий, ветка `main`.
3. Build pack: Dockerfile / Nixpacks (Nixpacks сам определяет Python, Node и т.п.).
4. **Domains**: `проект.твойдомен.ru` — сертификат Let's Encrypt выпустится сам.
5. **Environment Variables** — то, что лежит в `.env`.
6. Deploy. Дальше push в `main` → автодеплой по вебхуку.

Внутренняя БД, если нужна: **New → Database → PostgreSQL**, подключается к
приложению по имени сервиса внутри общей docker-сети — наружу порт не открывать.

### Важно для сервисов с фоновым воркером

Если у приложения есть long polling или воркер уведомлений (например
Telegram-бот), воркер должен жить **строго в одном экземпляре**:

* держать один сервис, без масштабирования реплик;
* в настройках приложения включить **stop before deploy** (сначала гасим
  старый контейнер, потом поднимаем новый), а не rolling update с перекрытием —
  иначе на время деплоя работают два процесса и уведомления уходят дважды;
* healthcheck на такой сервис вешать по внутреннему признаку, а не по HTTP-порту,
  которого у воркера нет.

Веб-часть и воркер лучше развести на два приложения в одном проекте: у веба —
домен и HTTPS, у воркера — только исходящие соединения.

## Чужой проект на этом же сервере

Единица изоляции в Coolify — команда (Team). Сервер принадлежит ровно одной
команде и между командами не шарится (мейнтейнеры это подтверждают, обещают в
v5), а внутри команды роль `member` видит все проекты и все переменные окружения
и может удалить чужой ресурс. Значит «пустить в панель, но в песочницу» не
получится: либо человек — доверенный совладелец всего, либо ему нужен отдельный
VPS со своим Coolify, либо он вообще не заходит в панель, а его проект
разворачиваешь ты. Ниже — последний вариант.

Схема: репозиторий остаётся его, ключ на чтение и вебхук он добавляет у себя
один раз, приложение в Coolify заводишь ты. Дальше его `git push` в `main` едет
на прод сам, без твоего участия.

### 1. Ключ к чужому репозиторию

Если репозиторий публичный — шаг пропускается, в Coolify выбирается
**Public Repository** и вставляется https-ссылка.

Для приватного: Coolify → **Keys & Tokens → Private Keys → + Add** →
сгенерировать новый SSH-ключ (имя, например, `partner-repo`), скопировать
публичную часть.

Владелец репозитория у себя: **Settings → Deploy keys → Add deploy key**,
вставляет ключ, галочку **Allow write access не ставит**. Ключ read-only и
действует только на этот один репозиторий.

Свой GitHub App здесь не подходит: он установлен в твой аккаунт и репозитории
чужого аккаунта не видит.

### 2. Приложение

1. **Projects → + Add** — отдельный проект, чтобы чужие ресурсы не мешались с
   твоими в списке.
2. Внутри: **+ New → Application → Private Repository (with deploy key)**
   (или **Public Repository**).
3. Выбрать ключ `partner-repo`, вставить SSH-ссылку
   `git@github.com:логин/репозиторий.git`, ветка `main`.
4. Build pack: Nixpacks (сам определит Node, Python и т.п.) или Dockerfile,
   если он есть в репозитории.
5. **Domains**: `проект.твойдомен.ru` — wildcard-запись уже есть, сертификат
   выпустится сам.
6. **Environment Variables** — содержимое его `.env`. Хранится у тебя в панели.
7. **Deploy**.

Нужна БД — **New → Database → PostgreSQL** в том же проекте, порт наружу не
публиковать, расписание бэкапов на вкладке Backups.

### 3. Автодеплой по push

С deploy key вебхук ставится руками.

У тебя: приложение → вкладка **Webhooks** → блок ручных вебхуков. Там URL вида
`https://coolify.твойдомен.ru/webhooks/source/github/events/manual` и поле
секрета — задать секрет и сохранить. URL копировать из UI, не набирать руками.

У него: репозиторий → **Settings → Webhooks → Add webhook**:

| Поле | Значение |
|---|---|
| Payload URL | URL из вкладки Webhooks |
| Content type | `application/json` |
| Secret | секрет оттуда же |
| События | Just the push event |

Проверка: пуш в `main` → в GitHub у вебхука зелёная галочка в **Recent
Deliveries**, в Coolify стартует деплой.

### 4. Обратная связь без доступа к панели

**Notifications** в настройках команды → Telegram или почта, события
*Deployment success* и *failed*. Человек сам видит, доехал ли его пуш, и не
дёргает тебя по каждому коммиту.

### 5. Чтобы чужая сборка не роняла твоё

* В настройках приложения выставить **Memory Limit** (~1 ГБ) и **CPU Limit**
  (~1) — на 4 ГБ RAM это спасает от «сборка съела всю память».
* Портов наружу не публиковать, трафик только через Traefik по домену.
* Следить за местом: ниже ~8 ГБ свободного сборки начинают падать.

### Пример: воркер без домена

Разбор файлов с Битрикс.Диска (`dd-cheki`): образ на базе `python:3.12-slim`
плюс `tesseract-ocr`, ~400 МБ; фоновый цикл раз в 10 минут, HTTP наружу не
торчит, состояния нет — временные файлы через `tempfile`, всё остальное живёт в
Битриксе. Ни домена, ни тома, ни базы. Собирается прямо на сервере.

1. **Keys & Tokens → Private Keys → + Add** → сгенерировать ключ `dd-cheki`,
   публичную часть отдать владельцу репозитория (Deploy keys, без write access).
2. **Projects → + Add** → проект → **+ New → Application → Private Repository
   (with deploy key)** → ключ `dd-cheki`, ссылка
   `git@github.com:логин/dd-cheki.git`, ветка `main`.
3. Build pack — **Dockerfile**. **Domains** оставить пустым,
   **Ports Exposes** тоже: порта нет, Traefik тут не участвует.
4. **Healthcheck выключить.** Проверка по умолчанию ходит HTTP-запросом на
   порт; у воркера его нет, контейнер получит статус unhealthy и деплой будет
   помечен как упавший, хотя процесс жив.
5. **Stop before deploy включить.** Rolling update поднимает новый контейнер до
   остановки старого — полминуты два процесса разбирают одну и ту же входящую
   папку, и в Битрикс уезжает дубль.
6. **Environment Variables**, все runtime — галочку *Build Variable* не ставить
   ни на одной, иначе секрет запечётся в слои образа:

   | Переменная | Значение |
   |---|---|
   | `BITRIX_WEBHOOK` | входящий вебхук портала, единственный секрет |
   | `DISK_FOLDER_IN` / `DISK_FOLDER_OK` / `DISK_FOLDER_BAD` | id папок на Диске |
   | `INTERVAL_SEC` | период опроса, `600` |
   | `TG_BOT_TOKEN`, `TG_CHAT_ID` | уведомления, необязательно |
   | `DRY_RUN` | `1` на первый запуск |

7. Лимиты: **Memory 1 ГБ**, **CPU 1**. Tesseract упирается в процессор, и без
   лимита распознавание многостраничного скана заметно подтормаживает соседние
   сайты.
8. **Deploy**, дальше смотреть вкладку **Logs** — для воркера это единственное
   окно наружу.
9. Вебхук на push настроить как в разделе выше.
10. Убедившись по логам, что цикл ходит в Битрикс и видит файлы, поменять
    `DRY_RUN` на `0` и нажать **Redeploy**.

Пункты 1–7 умеет сделать скрипт — пригодится, если таких воркеров будет
несколько. Токен: **Keys & Tokens → API tokens**, права на чтение и запись.

```bash
cp dd-cheki.env.example dd-cheki.env   # вписать боевые значения
COOLIFY_URL=https://coolify.твойдомен.ru ENV_FILE=./dd-cheki.env \
  bash scripts/05-deploy-worker.sh
```

Токен он спросит сам, скрытым вводом, чтобы тот не осел в истории команд.
Ничего не удаляет и не трогает существующие ресурсы, повторный запуск
переиспользует созданное раньше и просто обновляет переменные. Деплой сам не
запускает — только с `DEPLOY=1`. В конце печатает публичный ключ и секрет
вебхука: это то, что надо передать владельцу репозитория.

Что настраивается через переменные скрипта: `APP_NAME`, `PROJECT_NAME`,
`GIT_REPO`, `GIT_BRANCH`, `MEMORY`, `CPUS`, `SERVER_UUID` (нужен, только если
серверов больше одного). «Stop before deploy» в API Coolify не вынесен —
эту галочку всё равно ставить руками, скрипт про неё напомнит.

Про лимит памяти стоит помнить вот что: Docker не тормозит процесс при
превышении, а убивает контейнер. Если это случится посреди разбора файла,
файл останется во входящей папке и на следующем цикле будет разобран заново —
проверь, что повторная обработка не создаёт второй счёт в Битриксе. То же
касается любого падения воркера, так что свойство полезное само по себе.

### Границы

Он не может: зайти в панель, увидеть твои переменные, удалить твои проекты,
попасть на сервер. Ты не можешь: писать в его репозиторий — ключ read-only.
Логи, передеплой и правка env-переменных остаются на тебе.

Если такой ручной режим надоест, честная альтернатива — второй VPS со своим
Coolify: те же три скрипта, `SERVER_IP=<новый> HOST_ALIAS=<алиас> bash
scripts/01-local-keys.sh`, а поддомены увести на новый IP отдельными
A-записями.

## Что стоит знать про эту конфигурацию

**ufw и Docker.** Docker пишет свои правила в iptables в обход ufw, поэтому
опубликованный наружу порт контейнера (`ports: 8080:8080`) будет доступен из
интернета, даже если ufw его не разрешал. Практический вывод: не публикуй порты
приложений вообще — пусть трафик идёт только через встроенный в Coolify Traefik
по доменам. Базы данных держи без публикации портов.

**root по SSH остаётся включённым (только по ключу).** Это не недосмотр:
Coolify управляет собственным хостом по SSH под root и складывает свой ключ в
`/root/.ssh/authorized_keys`. Полный `PermitRootLogin no` ломает деплой.

**Бэкапы.** В Coolify: **Settings → Backup** — регулярный дамп его собственной
БД, плюс у каждой управляемой базы своя вкладка Backups с расписанием и выгрузкой
в S3. Настрой это до того, как на сервере окажется что-то ценное.

**Место на диске.** Coolify хочет 20 ГБ свободного места и предупреждает, если
меньше, но установку не прерывает. Сам он занимает ~5 ГБ, остальное съедают
образы и кеш сборок. Скрипт ставит `/etc/cron.weekly/docker-prune` — раз в
неделю удаляются образы и слои старше 7 дней, не связанные с контейнерами;
тома с данными не трогаются. Посмотреть, что занято, и почистить руками:

```bash
ssh coolify 'docker system df'          # что сколько ест
ssh coolify 'docker image prune -af'    # снести неиспользуемые образы
ssh coolify 'docker builder prune -af'  # снести кеш сборок
```

Если свободного меньше ~8 ГБ, сборки начнут падать с `no space left on device`.
На таком диске лучше собирать образы не на сервере, а в GitHub Actions, и
деплоить готовый образ из registry.

**Ресурсы.** Coolify в покое занимает ~1 ГБ RAM. Сборка образов — самая
прожорливая часть, поэтому скрипт добавляет swap при RAM < 4 ГБ. Для нескольких
лёгких сайтов 4 ГБ комфортно, на 2 ГБ жить можно, но сборки лучше делать не
одновременно.

## Если что-то пошло не так

```bash
ssh coolify 'bash -s' < scripts/04-status.sh          # общая картина
ssh coolify 'docker logs -n 100 coolify'              # логи панели
ssh coolify 'docker ps -a'                            # что упало
ssh coolify 'docker logs -n 100 coolify-proxy'        # Traefik: TLS, роутинг доменов
ssh coolify 'journalctl -u ssh -n 50'                 # проблемы с SSH
```

Сертификат не выпускается — почти всегда DNS ещё не разъехался или домен ведёт
не на этот IP: проверь `dig +short домен` и что порт 80 открыт (Let's Encrypt
ходит по HTTP-01).

**Сервер пропал из сети целиком (не идёт даже ping), но VNC-консоль работает** —
мост Docker занял подсеть шлюза хостера. Установщик Coolify по умолчанию отдаёт
Docker пул `10.0.0.0/8`, а многие провайдеры маршрутизируют VPS через `10.x`;
тогда `docker0` присваивает себе адрес шлюза, и весь трафик уходит в никуда.
Диагноз виден в `ip route` — адрес после `default via` совпадает с `src` у
`docker0`. Лечение из консоли:

```bash
systemctl stop docker docker.socket
ip link del docker0                       # связь возвращается сразу
ip link del $(ip -br link | awk '/^br-/{print $1}')

cp /etc/docker/daemon.json /etc/docker/daemon.json.bak
cat > /etc/docker/daemon.json <<'EOF'
{ "default-address-pools": [ { "base": "172.28.0.0/14", "size": 24 } ],
  "bip": "172.27.0.1/24" }
EOF
systemctl start docker
docker network rm coolify     # пересоздастся в новом диапазоне
ping -c 3 8.8.8.8
```

Скрипт `02-server-setup.sh` подбирает непересекающийся диапазон сам и проверяет
связность после установки, так что повторно это возникнуть не должно.

**`Connection timed out` на порт 22, хотя раньше пускало** — почти наверняка
fail2ban забанил твой IP после серии неудачных попыток. DROP в iptables даёт
именно таймаут, а не отказ. Бан снимается сам через час; снять сразу можно
только из веб-консоли хостера:

```bash
fail2ban-client status sshd                  # список забаненных
fail2ban-client set sshd unbanip <твой-IP>   # свой IP: curl ifconfig.me
```

Скрипт вносит IP, с которого он был запущен, в `ignoreip`, так что при
запуске через `ssh coolify` этой ситуации возникать не должно. Если ставишь
из консоли хостера, укажи адрес явно:
`ssh coolify 'ADMIN_IP=1.2.3.4 bash -s' < scripts/02-server-setup.sh`

Заблокировал себе SSH — заходи через веб-консоль (VNC) хостера и откатывай:
`rm /etc/ssh/sshd_config.d/99-hardening.conf && systemctl restart ssh`.
