# Переезд Coolify на новый сервер с бэкапом из S3

Старый сервер умер, новый — чистая Ubuntu на `185.20.139.146` (старый был
`95.85.242.143`; при следующем переезде подставь свой новый IP). Задача: поднять
Coolify, вернуть в него все проекты из бэкапа в S3 и данные баз проектов.

Облачная сессия Claude сюда не годится: из её контейнера наружу открыт только
HTTPS на 443, порт 22 закрыт, по SSH на сервер не попасть. Поэтому всё ниже
выполняется **на самом сервере** — руками или сессией Claude Code, запущенной
прямо там (шаг 2).

## Что нужно иметь на руках

| Что | Где взять |
|---|---|
| пароль root нового сервера | письмо/панель хостера |
| SSH-ключ | сейчас это `~/.ssh/id_ed25519_pppp` (комментарий `Cursor_PPPP`), раньше — `~/.ssh/coolify_ed25519`; нет — `01-local-keys.sh` создаст новый. Ключ с нестандартным именем ssh сам не предлагает: нужен `-i` или `IdentityFile` в `~/.ssh/config` |
| копия `.env` нового Coolify | `Dropbox/programming/coolify-setup/` |
| S3: endpoint, бакет, access/secret key | панель S3-провайдера; это то же хранилище, что было в Coolify → Storages |
| **APP_KEY старого Coolify** | строка `APP_KEY=base64:...` из старого `/data/coolify/source/.env`. Поищи копию в Dropbox, менеджере паролей, заметках |
| версия старого Coolify | если помнишь; README упоминает 4.1.2 |

Без старого APP_KEY дамп восстановится, но зашифрованные поля — переменные
окружения приложений, приватные ключи, ключи S3 — будут нечитаемы. Тогда проще
развернуть чистый Coolify и завести проекты заново, а из S3 вернуть только
данные баз (шаг 6).

## 1. С компьютера: ключ на новый сервер

Если IP остался прежним, а сервер другой, SSH ругнётся «REMOTE HOST
IDENTIFICATION HAS CHANGED» — забудь старый отпечаток (в bash — WSL или Git Bash):

```bash
ssh-keygen -R <IP сервера>
```

Если IP новый, поправь `HostName` у алиаса `coolify` в `~/.ssh/config`, иначе
`ssh coolify` пойдёт на старый адрес. План переезда может содержать IP старого
сервера — сверяй с тем, что показывает хостер (`curl -4 ifconfig.me` на сервере).

```bash
cd ~/Dropbox/programming/coolify-setup && git pull
```

```bash
bash scripts/01-local-keys.sh
```

Спросит пароль root один раз. Если `coolify_ed25519` лежит не в `~/.ssh`, укажи
путь: `KEY_PATH=/путь/к/coolify_ed25519 bash scripts/01-local-keys.sh`.

## 2. На сервере: Claude Code (по желанию)

Если дальше всё делает Claude, его удобнее запустить прямо на сервере: оттуда
открыт и S3, и Docker, и SSH не нужен вовсе.

```bash
ssh coolify
```

```bash
curl -fsSL https://claude.ai/install.sh | bash
```

```bash
git clone https://github.com/AlexB0nch/Coolify.git /root/coolify-setup && cd /root/coolify-setup
```

```bash
~/.local/bin/claude
```

При первом запуске он даст ссылку на вход в аккаунт claude.ai. Внутри сессии
`/remote-control` выводит её в приложение Claude — можно продолжать с телефона.
Первое сообщение:

> Прочитай docs/переезд-на-новый-сервер.md и выполни шаги 3–7 на этом
> сервере. Ты на нём под root. Ключи S3 и APP_KEY спроси у меня.

## 3. Базовая установка

С компьютера (или на сервере: `bash scripts/02-server-setup.sh`):

```bash
ssh coolify 'bash -s' < scripts/02-server-setup.sh
```

Обновление, ufw, fail2ban, swap, Coolify последней версии. Если старый
Coolify был заметно старее — неважно: при восстановлении установщик
перезапускается и прогоняет миграции на дамп. Нужна точная версия —
`COOLIFY_VERSION=4.1.2` в шаге 4.

**Админа в панели на этом этапе не заводить по-настоящему** — после
восстановления в силе будут старые логины. Но порт 8000 открыт, а регистрация
открыта до первого пользователя, поэтому до шага 4 стоит либо быстро пройти
этот шаг, либо завести временного админа со сложным паролем — он будет
стёрт дампом.

## 4. Восстановление Coolify из S3

На сервере:

```bash
cd /root/coolify-setup && S3_ENDPOINT=https://<endpoint> S3_BUCKET=<бакет> bash scripts/07-restore-from-s3.sh
```

Скрипт спросит скрытым вводом S3-ключи и старый APP_KEY, найдёт самый свежий
`*.dmp` бэкапа Coolify, проверит его, сохранит текущую БД и `.env` для отката,
сделает `pg_restore`, перезапустит установщик и пропишет ключ localhost в
`authorized_keys`. Варианты: `S3_PREFIX=` — сузить поиск, `S3_KEY=` — взять
конкретный файл, `BACKUP_FILE=` — дамп уже на сервере. Для AWS `S3_ENDPOINT`
не нужен, нужен `S3_REGION`.

Проверка: `http://<IP сервера>:8000` пускает по **старому** логину, проекты на
месте, у приложения открываются переменные окружения без ошибки про MAC.
**Servers → localhost → Validate** — зелёный.

Посмотреть, что лежит в S3, ничего не восстанавливая: `LIST_ONLY=1` с теми же
`S3_ENDPOINT`/`S3_BUCKET`. Скрипт сам создаёт сети назначений Docker (иначе базы
не стартуют с «network … declared as external, but could not be found») и
перегенерирует конфиг Traefik для панели (иначе домен панели отдаёт 503).

## 5. DNS

A-записи `домен`, `coolify.домен`, `*.домен` → IP нового сервера. Если IP
сменился — поменять их у регистратора (для alexshein.com, alex-shine-the-new-king.com.ru
и natabiz.ru это DNS-редактор Timeweb hosting), проверить `dig +short coolify.домен @8.8.8.8`.

Let's Encrypt выдаёт сертификат только когда домен уже смотрит на новый IP.
Если прокси пытался раньше, срабатывает лимит — 5 неудачных попыток на домен в
час. Подожди час и перезапусти прокси (`docker restart coolify-proxy`): Traefik
перезапрашивает сертификаты при старте, обновления файлов конфига ему мало.

Домены вида `*.<старый IP>.sslip.io`, которые Coolify генерирует сам, после смены
IP перестают работать — их надо поправить или убрать в настройках приложения.

## 6. Базы проектов

Бэкап Coolify — это только настройки панели. Ресурсы БД после шага 4 есть в
списке, но их тома на новом сервере пустые. Для каждой базы:

1. открыть базу → **Start** (поднимется пустая);
2. **Backups** → нужное расписание → в списке выполнений найти последнее,
   загруженное в S3 → **Restore** (в разных версиях — **Import Backup** с
   выбором файла из S3);
3. после этого **Redeploy** приложений, которые к ней ходят.

Файлы в томах приложений (загрузки, sqlite и т.п.) Coolify в S3 не кладёт —
их можно вернуть только если они бэкапились отдельно.

Как это было на практике (ноябрь 2026): кнопкой Restore не пользовались.
Дампы баз из S3 восстанавливались `pg_restore` **внутри контейнера самой базы**:
формат дампа привязан к мажорной версии PostgreSQL, а у `coolify-db` PG15 и
дампы PG16/PG18 он не читает. Тома, которые бэкапились отдельно архивами
`tar.gz`, распаковывались в остановленный том:
`docker run --rm -v ТОМ:/v -v ПАПКА:/b:ro alpine tar xzpf /b/ФАЙЛ -C /v --numeric-owner`.
Сырой каталог PGDATA сначала проверяли на временном томе (crash recovery,
`pg_dump`), и только потом клали в боевой.

## 7. Приложения и финиш

* Redeploy всех приложений: **Projects → ресурс → Redeploy**. Для воркеров —
  Consistent Container Names остаётся включённым, оно в БД.
* Вебхуки GitHub менять не надо: домен тот же.
* В Settings инстанса обновить публичные IPv4/IPv6, если IP сменился.
* Settings → Backup: убедиться, что бэкап самого Coolify в S3 снова по
  расписанию, и **сохранить новый `/data/coolify/source/.env`** (в нём APP_KEY)
  туда же, где будешь искать его в следующий раз.
* Закрыть вход по паролю: `ssh coolify 'bash -s' < scripts/03-harden-ssh.sh`.
* Общая картина: `ssh coolify 'bash -s' < scripts/04-status.sh`.

## Если что-то пошло не так

* `pg_restore` упал — контейнеры остаются остановленными. Откат: вернуть
  `/data/coolify/source/.env.before-restore-*` и восстановить
  `/data/coolify/backups/restore/fresh-install-*.dmp` той же командой
  `pg_restore`, затем перезапустить установщик.
* «The MAC is invalid» / ошибки шифрования — APP_KEY не тот. Поменять в
  `.env`, `docker restart coolify`.
* localhost не валидируется — ключ из **Keys & Tokens** не в
  `/root/.ssh/authorized_keys`. Скрипт делает это сам, но если не смог —
  скопировать публичную часть из панели руками.
